# 游戏开发 Agent Loop

> 状态：项目强制开发流程  
> 版本：v1.1  
> 更新日期：2026-09-01

## 1. 目标

每个可玩功能都经过“方案—实现—运行—试玩—截图—判断—修复—回归”的闭环。代码通过编译不代表功能完成；视觉正确但规则错误也不代表完成。

本流程适用于：

- 新玩法和角色行为。
- 武器、敌人、Boss 和波次。
- HUD、升级、商城和菜单。
- 视觉反馈、动画、特效和性能优化。
- 影响玩家体验的缺陷修复。

纯文档讨论、只读分析和没有运行时影响的机械修改可以不执行浏览器阶段，但仍需完成与风险匹配的验证。

## 2. 状态机

```text
DESIGN
  ↓
IMPLEMENT
  ↓
STATIC_VERIFY ──失败──→ FIX
  ↓通过                 ↑
RUN                     │
  ↓                     │
PLAYTEST ─────失败──────┤
  ↓                     │
CAPTURE                 │
  ↓                     │
EVALUATE ─────失败──────┘
  ↓行为通过
UI_REQUIRED? ──否──→ REGRESSION
  ↓是
VISUAL_SPEC → ASSET_CREATE → NORMALIZE → INTEGRATE
  ↓
STATIC_VERIFY → RUN → PLAYTEST → CAPTURE → EVALUATE
  ↓视觉通过
REGRESSION
  ↓通过
COMPLETE / NEXT ACCEPTED FEATURE
```

## 3. DESIGN：先定义可验证目标

开始编码前记录：

- 功能名称和范围。
- 对应 GDD 章节。
- 玩家能够观察到的行为。
- 正常流程、失败流程和边界输入。
- 明确不实现的内容。
- 自动检查与浏览器检查方式。

验收标准必须可观察，例如“按住 W 时熊猫向上移动，松开后停止”，不能只写“移动正常”。

如果需求与 GDD 冲突，停在 DESIGN 阶段，先请求设计确认。

## 4. IMPLEMENT：最小垂直切片

- 只实现当前验收标准需要的最少代码和资源。
- 优先复用浏览器、Phaser 和平台原生能力。
- 不提前实现下一里程碑。
- Simulation 保存规则状态，Renderer 负责表现，DOM UI 只展示和发出意图。
- 随机行为保留可复现种子。

## 5. STATIC_VERIFY：静态与自动检查

按项目实际脚本执行：

1. 类型检查。
2. 构建。
3. 与当前功能直接相关的自动测试。
4. 必要时检查格式或静态分析。

任何失败都先修复，再启动视觉验证。不要用截图掩盖编译或运行错误。

## 6. RUN：启动真实游戏

- 使用与玩家一致的入口启动开发服务器。
- 记录实际访问地址。
- 检查控制台和终端是否存在错误。
- 确认首个可操作画面出现。
- 不用静态 HTML 截图替代真实 Phaser 运行时。

## 7. PLAYTEST：按玩家路径操作

至少验证：

- 首次进入是否可操作。
- 当前功能的主要动作。
- 输入开始、持续和结束状态。
- 暂停或 UI 覆盖时输入是否被正确阻断。
- 失败、受伤、死亡或无目标等相关边界状态。
- HUD 是否遮挡战场。
- 危险预警是否比粒子和伤害数字更清楚。

Canvas/WebGL 功能不能只依赖 DOM 断言，必须观察渲染结果。

## 8. CAPTURE：截图证据

本地证据目录：

```text
artifacts/agent-loop/<task-slug>/iteration-<nn>/
```

命名建议：

- `01-initial.png`：进入功能后的初始状态。
- `02-active.png`：主要动作执行中。
- `03-result.png`：动作完成、成功或失败状态。
- `04-edge-case.png`：重要边界状态。
- `notes.md`：预期、观察结果和问题清单。

只保存能证明验收标准的截图，不为凑数量重复截图。

## 9. EVALUATE：预期与观察对比

逐条回答：

| 检查 | 结果 |
|---|---|
| 行为是否符合 GDD 和验收标准 | 通过 / 失败 |
| 玩家是否能理解当前状态 | 通过 / 失败 |
| 战场中心和移动区域是否清晰 | 通过 / 失败 |
| 输入、碰撞和计时是否正确 | 通过 / 失败 |
| 控制台和终端是否无新增错误 | 通过 / 失败 |
| 当前功能是否破坏邻近功能 | 通过 / 失败 |

失败项必须包含：玩家看到什么、如何复现、为什么重要、最可能属于哪个子系统。

## 10. UI_REQUIRED：玩家可见功能必须经过美化判断

功能规则通过后必须记录：

```text
UI_REQUIRED = yes / no
理由 = 玩家会看到哪些新增或变化的元素
涉及元素族 = 角色 / 敌人 / 武器 / 道具 / 掉落物 / HUD / 菜单 / 场景 / 特效
```

以下情况默认是 `yes`：新增或修改角色、敌人、武器、道具、掉落物、状态图标、HUD、菜单、奖励、危险提示、场景或玩家反馈。

`yes` 时必须先读取 `docs/VISUAL_DESIGN_SYSTEM.md`。如果没有对应元素族规范，先定义用途、源画布、运行时尺寸、透明边距、锚点、轮廓、色板、光源、状态变体和命名，再开始生成或绘制。功能占位图只能用于规则验证，不能跨过完成门。

资产完成后必须：

1. 保存到项目资源目录，不引用临时位置。
2. 统一裁切、透明度、缩放和锚点。
3. 替换运行时占位视觉。
4. 在真实游戏尺寸下检查，而不是只看原始大图。
5. 重新执行静态验证、浏览器试玩、截图对比和回归。

## 11. FIX：最小根因修复

- 根据证据定位根因，不针对单张截图做表面补丁。
- 搜索相关调用路径后在共同入口修复。
- 不顺手重构无关代码。
- 每次修复后重新执行 STATIC_VERIFY、RUN、PLAYTEST、CAPTURE 和 EVALUATE。
- 迭代目录按 `iteration-01`、`iteration-02` 递增，保留最终通过证据。

## 12. REGRESSION：完成前回归

最后一次修复通过后验证：

- 当前功能全部验收标准。
- 与其直接相邻的输入、HUD、碰撞、计时和场景生命周期。
- 构建仍然通过。
- 最终截图来自最后一次代码状态。

视觉或运行时代码在最后截图后再次改变，原截图失效，必须重新验证。

## 13. 完成与继续条件

只有同时满足以下条件才可以标记完成：

- 验收标准全部通过。
- 自动检查通过。
- 真实浏览器路径已操作。
- 当前代码状态有截图证据。
- 已记录 `UI_REQUIRED`，需要 UI 时已按统一元素族规范替换占位视觉。
- 最后一次修复后完成回归。
- 未通过修改 GDD 来迁就实现。

完成当前功能后，只能继续用户已经批准的下一项功能或里程碑。Agent Loop 提供持续执行能力，但不扩大任务授权。

## 14. 停止条件

遇到以下情况必须停止并请求用户处理：

- 需要改变已确认的游戏设计。
- 需要扩展到未批准的里程碑。
- 需要外部账号、密钥、付费资源或新的权限。
- 需要破坏性操作或不可恢复的数据修改。
- 浏览器或运行环境无法提供必需验证证据。
- 同一阻塞条件经过三轮有证据的修复仍未解决。

## 15. 完成报告格式

每个功能完成时至少报告：

- 实现了什么。
- 对应 GDD 章节。
- 执行了哪些自动检查。
- 浏览器实际操作了什么。
- 截图证据路径。
- 修复过哪些问题。
- `UI_REQUIRED` 判断、采用的元素族规范和最终资产路径。
- 哪些内容明确没有实现。
