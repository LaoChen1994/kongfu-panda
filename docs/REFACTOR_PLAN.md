# 游戏工程重构计划

> 版本：v1.1<br>
> 日期：2026-10-03<br>
> 状态：R0 与独立构建入口已完成；R1～R6 及 R7 剩余部分待执行<br>
> 工作分支：`codex/project-structure`<br>
> 产品基线：GDD v3.2 第 20 章，兼容第 18、21、25 章；R0 行为基线采集于 v3.1<br>
> 代码基线：MR #25 合并后的 main，`ebadff30197e401516c5fa36a65d4488800eb7c9`

本计划把现有内容配置、战斗规则、输入、渲染、界面和平台接入按职责分开，补充可以定位失败原因的单元测试。重构不改变玩法、数值、随机顺序、存档格式、美术与用户操作。每个部分单独实现、验证和审查，前一部分通过后才进入下一部分，不把目录调整与玩法优化放在同一批修改中。

## 1 当前结构与问题

当前 `src/main.ts` 为 1,628 行，包含应用启动、设置与战绩、资源加载、开发夹具、Phaser 场景、键盘与触控、动画与特效、HUD、升级、商城、暂停和结算。`src/simulation.ts` 为 1,425 行，包含内容表、实体类型、初始化、属性重算、经济、升级以及战斗与波次规则。`src/simulation.test.ts` 为 982 行，串行执行领域断言，并导入双语和 Poki 测试。

具体整理目标：

- 角色初始属性目前在初始化、属性重算和选人显示中重复定义，统一为角色基础配置。
- 敌人、Boss、武器和道具触发规则集中在 `stepGame` 及其辅助函数中，按现有规则职责拆分，不创造通用技能语言。
- 动画帧表、加载路径、运行尺寸和攻击尺寸补偿分散，建立明确的资源与显示配置。
- 全局 DOM、窗口事件和场景对象交织，明确初始化、重开、返回选人及销毁时的生命周期。
- Pages 工作流目前只安装和构建，没有执行规则测试；新增独立 PR 检查，不改变现有 Pages 发布时机。

保留现有优势：Simulation 不依赖 Phaser，规则使用可复现随机种子；Poki、双语与战绩已存在独立模块；DOM 负责文字，Phaser 负责战场。

## 2 范围与约束

### 2.1 本轮包含

- 现有角色、敌人、武器、道具、强化定义与运行状态的组织。
- 现有战斗、经济、成长、波次与 Boss 实现的职责分离。
- 输入、动画、特效、资源加载、DOM UI、持久化及平台模块边界。
- 单测组织、行为基线、内容校验、生命周期测试与 PR 检查。
- 对应的 GDD 架构说明和实际验证记录。

### 2.2 本轮不包含

- 新角色、怪物、道具、地图、货币、玩法、存档续局和永久养成。
- 数值平衡、调整帧率或 Simulation 步长、空间索引、对象池改造与性能承诺。
- 新动作引擎、ECS、实体继承树、依赖注入容器、通用事件总线、插件系统或通用状态机框架。
- 图片生成、资源重命名、重新压缩、音效开发、Windows 分发或 Poki 正式发布。
- 新测试平台、浏览器自动化依赖或以覆盖率百分比作为唯一完成条件。

### 2.3 重构红线

1. 稳定 ID、localStorage 键、存档版本、默认语言规则和应用 identifier 不变。
2. 随机算法、随机调用次数与顺序、实体 ID 分配、实体遍历顺序、同帧处理顺序不变。
3. 保留现有暂停、失焦、广告、升级、商城、胜负和竖屏阻断语义；不混用“暂停规则”和“暂停动画”。
4. 不改变素材路径、锚点、显示尺寸、动画补偿与危险预警层级。
5. 纯重构测试不允许自动刷新预期结果掩盖差异；发现原有问题先记录，玩法修复单独确认。
6. 依赖使用包管理器添加；本计划优先采用 Node 内置测试能力，不新增游戏运行时依赖。
7. 不因文件长就机械切段，不用万能 `utils.ts` 或大杂烩 `types.ts` 替代原大文件。
8. 类型靠近所属领域；不使用 `as any`、深层继承或只用于美化代码的单次 helper。通用 helper 必须满足项目的三处调用、自然类型和降低复杂度要求。
9. 模块导入不能形成运行时循环。若某个新系统入口需要突破单次抽取约束，在该阶段实现前说明具体必要性并确认，不以“工程化”为理由自动豁免。

## 3 目标结构与职责

下面是目标组织方式，不是要求一次创建全部文件。文件仅在对应阶段需要真实承接职责时建立，不创建空目录或重复导出的包装层。

```text
src/
  main.ts
  game/
    content/
      characters.ts
      enemies.ts
      weapons.ts
      items.ts
      upgrades.ts
    simulation/
      state.ts
      player.ts
      enemy.ts
      combat.ts
      build.ts
      shop.ts
      progression.ts
      waves.ts
      step.ts
  phaser/
    assets/
      manifest.ts
      animations.ts
    scenes/
      BattleScene.ts
    input/
      controls.ts
    view/
      actors.ts
      effects.ts
      pickups.ts
      battlefield.ts
  ui/
    roster.ts
    hud.ts
    choices.ts
    shop.ts
    pause.ts
    results.ts
    onboarding.ts
  persistence/
    records.ts
    settings.ts
  platform/
    poki.ts
  i18n/
    i18n.ts
    translations.ts
  dev/
    playtest.ts
```

模型分为三种，而不是让所有内容继承一个基类：

| 类型 | 示例 | 责任 |
| --- | --- | --- |
| 内容定义 | CharacterDefinition、EnemyDefinition、ItemDefinition | 基础配置、名称、稳定 ID、约束与资源引用 |
| 单局状态 | PlayerState、EnemyState、DropState、GameState | 位置、生命、冷却、持有数量及可序列化状态 |
| 行为实现 | 追击、冲刺、射击、伤害、商店命令 | 按状态执行现有规则，不持有 Phaser 或 DOM 对象 |

内容表与类型不读取 DOM、localStorage、Phaser 或 SDK。Simulation 是规则状态唯一来源。Renderer 持有可销毁的精灵和播放状态，不能按动画完成时间决定伤害。UI 发出已有购买、升级、换波等意图；应用协调层统一处理平台等待与生命周期。

资源清单、动画帧参数和显示配置属于 Phaser 层。即便配置与内容关联，也不能让规则层导入 Phaser。基础角色属性为唯一数据来源，初始化、属性重算和 UI 均读取它；文案继续经过现有双语模块，不以翻译结果作为业务判断依据。

## 4 分阶段执行与交付

所有阶段顺序执行。每阶段可以独立形成提交和 MR；“独立”表示具备自己的范围、验收和回退点，不表示可以跳过依赖或并行修改共享状态。创建 MR、提交远端和合并仍遵循用户当次授权。

| 阶段 | 工作 | 前置 | 完成门 |
| --- | --- | --- | --- |
| R0 | 回归基线与测试入口 | 分支确认 | 原实现行为记录完成，测试失败能定位领域 |
| R1 | 内容定义、基础属性与实体模型 | R0 | 内容校验通过，确定性结果一致 |
| R2 | 属性、商城与升级规则 | R1 | 购买出售、刷新锁定、强化边界及随机顺序一致 |
| R3 | 战斗、敌人、武器与波次规则 | R2 | 战斗契约、Boss 与整局回归一致 |
| R4 | 输入、会话协调与持久化 | R3 | 暂停、重开、存储、广告和触控生命周期通过 |
| R5 | 资源、动画与战场渲染 | R4 | 当前代码视觉、播放、尺寸和清理回归通过 |
| R6 | DOM UI 与启动入口 | R5 | 双语完整流程、布局与 UI 命令回归通过 |
| R7 | PR 检查、边界检查与生产验收 | R6 | 三种构建通过，无夹具泄漏，验证清单闭合 |

### R0 回归基线与测试入口

在修改实现前保留现有全部测试，盘点断言并按内容、属性、商城、升级、战斗、Boss、存档、双语和 Poki 归类。使用 Node 内置 `node:test` 与严格断言组织具名用例；如 TypeScript 需要 Node 类型声明，通过 pnpm 增加开发依赖，不增加运行时测试库。保留现有 tsc 编译后执行的方式，让 `pnpm test` 自动运行全部测试文件，不再靠一个大测试文件手动导入其他测试。

记录旧实现的固定种子行为结果：三名角色分别运行输入脚本，包含移动、闪避、升级选择、购买/出售、刷新、锁定与换波。普通整局、混合构筑和 Boss 另建场景，不能只使用一份免伤耐久模拟代表全部行为。

基线包含初始状态、关键时间点、当前随机种子与 nextId、实体状态、构筑、铜钱、选择池、伤害和承伤统计。测试用输入脚本和关键预期放入版本控制；大截图与日志放 `artifacts/`。不得保留第二套旧生产实现，只为比较而长期维护双份逻辑。

新增测试重点：同种子与输入的两次执行完全一致；不同种子仍遵守领域约束；升级、商城、胜利、失败状态不推进规则；现有 600 秒耐久场景继续通过。对已知行为有明确断言，不能只比较最终哈希而无法说明失败原因。

验收：新测试入口运行全部原测试和新增基线；失败输出具备名称与差异。此阶段不搬业务实现，不跑平衡实验、不改 UI。浏览器采集重构前代表画面作为后续对比，截图不作为后续新代码的验收证明。

### R1 内容定义与实体模型

按领域移出三名角色、六种普通敌人、专属与通用武器、24 件物品及强化配置；保留现有 ID、数值、描述和英文映射。把角色生命、护甲、移速等基础值统一为内容配置，替换现有重复来源。

把 GameState 内嵌实体形状整理为有业务含义的类型，先保持字段和运行形状不变。Boss 专属字段暂不通过重塑全部对象来追求类型完整；需要进一步改变形状时另做阶段内提案。内容定义与状态通过类型导入连接，不相互运行时导入。

新增单测：

- 三名角色、六种普通敌人、三件专属加五件通用武器、24 件道具数量正确，稳定 ID 唯一。
- 角色与专属武器映射有效；进化所需物品存在；物品最大堆叠与唯一约束有效。
- 初始生命山岚 20、青团 10、石墨 30，其他基础属性逐项与基线一致。
- 初始化与出售全部道具后的属性回到同一角色基线，极限叠加不产生额外收益。
- 配置引用的素材真实存在，双语文案覆盖保留；修改一份角色基础配置无需改三个分支。

验收：R0 对比一致；三角色选人、开局、属性显示和购买/出售浏览器回归。资源清单的制作留给 R5，不在 R1 改加载策略。

### R2 属性商城与升级规则

移动现有属性重算、伤害预览依赖、购买、出售、刷新、锁定、升级选择与换波补给相关实现。先迁移已有函数，再根据实际调用次数决定是否合并重复逻辑；不改随机权重，不调整满武器槽商品策略。

新增或细化单测：

- 普通加法、倍率叠加、上下限、购买/强化顺序与出售顺序；立即治疗不能被属性重算重复应用。
- 余额不足、错误槽位、未开店、唯一物品、最大堆叠、满级武器、专属武器资格。
- 多商品锁定、全部锁定、保留到下轮，同屏去重，商品售空后免费补齐，正常刷新扣费。
- 三选一去重、唯一强化、角色适用性、属性上限、免费与付费刷新、失败操作不改状态或随机种子。
- 商城与强化池的固定种子序列与 R0 一致，不只检查概率范围。

验收：完整购买、出售、锁定、刷新、升级及下一波路径通过；UI 展示属性差值与实际规则一致。该阶段不拆商城 HTML/CSS。

### R3 战斗敌人武器与波次规则

这是风险最高的部分，继续拆为三个连续子提交：R3a 伤害/治疗与触发，R3b 敌人/Boss 行为与生成，R3c 武器/弹道、掉落及主更新协调。每个子提交重跑全套确定性基线，不能一次移动整个 `stepGame` 后再查差异。

保留同帧处理顺序，尤其是计时、闪避结束触发、移动、生成、敌人攻击、武器、命中、击杀、拾取、升级、商店和结算。迁移前从现有源码记录实际顺序，计划中的职责描述不是更改更新顺序的授权。保留循环期间追加召唤物的现有遍历语义。

敌人按已有行为差异组织；需要同形分发时使用类型明确的 ID 映射，不引入基类工厂。物品的常驻属性和攻击/受伤/治疗/护盾触发保持不同职责，不为 24 件物品各造一个 class。

新增或细化单测：

- 伤害按实际生命损失统计；死亡目标、溢出、护甲、护盾、闪避、致命保命和反击。
- 击杀爆炸不连锁；齐射只计一次攻击；护盾刷新、破盾、治疗溢出和图腾衰减。
- 三角色被动、八件武器攻击与等级变化、三件专属进化、无目标、穿透与回射。
- 六种敌人各自移动与攻击边界，精英预警、冲刺、远程射击及区域生命周期。
- Boss 出场、根刺预警、冲击波、增援上限、半血阶段、狂暴、击杀胜利及最后一击统计。
- 闪避无敌和冷却、拾取金额与经验、波次边界、同帧结算优先级和实体数量限制。

验收：规则测试、固定种子逐点结果和 600 秒回归通过；真实浏览器覆盖普通战斗、混合武器、升级、失败和 Boss。自动免伤模拟仅证明循环和数量约束，不作为真人通关证据。

### R4 输入会话与持久化

将键盘与摇杆映射整理为输入模块，沿用 PlayerInput。明确窗口失焦、页面隐藏、竖屏、升级、商城、广告和结算如何阻断输入。分别归属加载、游戏开始保护、暂停、广告等待与重开，不用一个通用布尔值替代这些不同状态。

把设置解析与保存、战绩读取/累计/保存移到持久化模块，保留键、版本及失败提示。既有 PokiSession 保留，仅移动路径与集成归属；不改 SDK 事件策略。应用启动持有会话与 Phaser 实例，场景拥有可清理的输入和视图对象，重开不能多注册监听器。

新增或细化单测：输入归一化与对角移动、闪避仅消费一次、松手/取消/失焦归零；设置损坏、旧版本、存储抛错、语言选择；战绩单局一次、测试局不计成绩、三角色隔离；SDK 初始化失败、事件去重、广告等待重入与失败恢复。

浏览器验证真实 PointerEvent、多点触控、快捷键焦点、暂停/恢复、后台恢复、旋转和连续重开。存储与 SDK 可以注入最小测试替身，但不模拟整套 Phaser 或 DOM 来代替真实交互。若确认原生命周期缺陷，单独记录并说明修复与纯搬迁的区别。

### R5 资源动画与战场渲染

集中加载键和路径、动画帧数与播放速率、角色/敌人运行尺寸、锚点与攻击补偿。保持只加载所选角色及当前加载错误、超时行为，不在此阶段换图集或引入懒加载策略。

分离角色/敌人视图、弹道与特效、经验掉落和地面/Boss 预警。视图负责创建、同步、回收和销毁；Simulation 状态与事件驱动表现，动画结束不修改规则。scene 保留生命周期与协调，不持有所有表现实现。先迁移现有渲染块，避免新增抽象层与逐帧分配大状态副本。

新增单测：素材键引用与路径有效、动画帧完整、显示尺寸及攻击补偿正确、低动画设置的显示策略、静止/移动/攻击选择、垂直朝向保持、暂停冻结策略、移除实体的清理集合。仅在形成真实可测试业务边界时测试播放策略，不为单测抽出单次表达式。

验收：浏览器观察三角色连续行走、转向和完整攻击；普通与混合敌人、受击、经验吸取、危险预警；暂停/恢复、连开和重开后无旧图像、重复特效或监听器。原生 Tauri 再验证播放与资源加载。截图必须来自最终代码，不能用 R0 截图证明重构后表现。

### R6 DOM 界面与启动入口

按选人、HUD、强化、商城、暂停、结算和引导拆界面模块，把 scene 中 DOM 查询、HTML 拼装与事件绑定移到所属界面。保留现有 DOM ID、类名、CSS、文案、键盘入口和缓存行为，暂不按文件长度拆 CSS。

main 负责读取偏好、初始化平台与界面、创建/销毁游戏，并建立输入到规则、规则到表现的协调。继续使用 DOM，不迁移 React，不引入通用组件库。已有 i18n 模块只调整归属，不重做翻译系统。

新增单测：背包同名合并与总件数、属性差值、武器历史伤害、承伤分类、升级次数、结算状态与存档一次性、语言切换不改游戏状态。只给已有或本阶段合理独立的展示数据逻辑写单测，HTML 排版、焦点和滚动由真实浏览器验证。

## 5 单元测试策略

测试与领域实现就近组织，文件使用 `*.test.ts`，复杂输入脚本与基线放测试专属目录，不从生产入口导入。现有测试逐项迁移，不能因拆分把断言删掉。具名用例优先断言玩家可观察结果及状态不变量，而不是证明某个私有方法被调用。

| 层级 | 验证内容 | 不替代的验证 |
| --- | --- | --- |
| 单元测试 | 内容约束、属性、伤害、商店、升级、输入计算、存储、平台状态 | 图片观感和真实触控 |
| 确定性回归 | 固定种子、输入及操作下的逐点状态和随机顺序 | 数值是否好玩 |
| 整局模拟 | 600 秒规则循环、Boss、数量限制和统计 | 真人通关和设备性能 |
| 浏览器与原生试玩 | 加载、焦点、触控、动画、布局、平台集成 | 未测试硬件或真实广告 |

基线不能只采集最终胜负。至少覆盖初始、第一次升级、第一次商城、一次重开、Boss 招式/阶段、胜利和失败；普通、混合构筑、Boss 测试保持各自可复现。随机权重测试保留现有足够样本的统计检查，同时用固定种子序列约束重构没有改变调用顺序。

不同职责的时间保持原语义：Simulation 使用传入 elapsed 与现有上限，渲染帧 delta 只影响表现；测试注入明确时间，不依赖真实等待或随手添加定时器。对于 Phaser 精灵、WebView、真实广告，不声明已有纯单测覆盖全部行为。

测试失败必须能够报告用例名、种子、操作步骤和期望/实际值。发现旧行为缺陷时保留复现，先确认是否单独修复；不能一边改规则一边把基线更新成新的结果。

## 6 每阶段的执行循环

1. 阅读该阶段涉及源码及 GDD，记录文件范围、预期、非目标与本阶段新增测试。
2. 对原实现添加并运行特征测试，保存基线，确认原测试仍通过。
3. 以最小子提交迁移职责，不夹带玩法或格式重写。
4. 执行 `pnpm typecheck`、`pnpm test`、`pnpm build:web`、`pnpm build:poki`、`pnpm build:desktop` 和 `git diff --check`；失败先修复。原生验收使用 `pnpm build:mac`。
5. 涉及运行时行为的阶段使用 Codex 侧边浏览器静音试玩，不操作用户 Chrome；记录控制台、实际入口和操作。
6. 截取当前代码的初始、主要操作及结果/边界画面，逐项比较预期，失败回到最小修复。
7. 记录 `UI_REQUIRED`。纯搬迁且玩家可见元素完全不变时预期为 no，仍需视觉回归；若实际改变可见状态，则为 yes，按视觉规范重新评估，不默认生成新素材。
8. 最后一次修改后重复相关回归，审查差异，记录限制与尚未测试项，再更新阶段状态。

证据目录使用 `artifacts/agent-loop/refactor-rN/iteration-NN/`。验证笔记包含源码 commit 或未提交 diff 标识、构建模式、种子、命令结果、预期/实际、截图、修复与限制。截图在忽略目录，不替代仓库内的可执行测试。

## 7 提交回退与停止条件

每阶段只包含所属职责与相应测试，遵循 Conventional Commits 和 Codex 署名要求；提交前检查 changesets 配置及全部差异。按用户当次要求提交、推送或创建 MR，不把本计划当作自动发布授权。

每阶段起点记录上一个已验证提交。未合并问题保留当前工作，定位到所属阶段修复；已合并且需要回退时提出精准 revert 方案，取得确认后执行，不使用 reset hard 或覆盖用户改动。兼容旧入口的临时导出只在迁移期间保留，并指定在依赖迁完后删除，不形成永久多入口 API。

以下情况停止进入下一阶段：基线或随机序列出现未解释变化；需要改玩法/数值/存档；出现导入循环或抽象规则冲突；无法进行必需浏览器/原生验收；需要新权限或扩大依赖范围；同一问题三轮有证据的修复仍未通过。先报告具体差异与选择，不通过降低断言或改 GDD 来完成重构。
